# Local retrieval for Gemini

Aevra retrieves on the phone before constructing any Gemini request. It does not upload the database, images, or an entire history to create embeddings.

1. Parse the question into topic terms and an optional local-calendar date range. Supported date forms: today/my day, yesterday, this/last week (Monday-based calendar weeks), this/last month, past/last seven days, and an ISO date. Intersect that range with the user's selected day/keyword scope. Local date boundaries handle daylight saving changes.
2. For topic questions, query the existing SQLite FTS4 index using escaped Unicode prefix terms joined with OR. Read `matchinfo(..., 'pcnalx')` statistics for **every matching row** in the scope, with no newest-300 cutoff. Compute weighted BM25 using inverse document frequency, term-frequency saturation and document-length normalization. App names receive weight 2, package names 0.35 and OCR text 1.
3. Maintain a 128-candidate heap while scanning index statistics. Load OCR documents only for those candidates, suppress identical text within the same app/half-hour window, and retain at most 24 observations. Repeated visits in different time windows retain separate evidence IDs. Memory used for candidate selection is bounded independently of total history size; CPU/I/O still scale with the number of matches.
4. For broad requests without topic terms, sample at most 48 observations across indexed time buckets, including range endpoints. Avoid allocating a list of every history ID. This is a partial overview, not a complete record or an exact app-usage calculation.
5. Split long OCR into overlapping 600-character chunks with 120-character overlap. Prefer matching chunks, preserve their order within a record, and include timestamp, app, provenance, quality and original observation ID. Selected records are rendered chronologically after budgeting in retrieval-rank order. Excerpt trimming centers on a matching word; per-record UTF-8 allowances preserve multilingual overview coverage. Explicit viewer selections bypass topic matching.
6. Cap evidence at **18,000 characters AND 24,000 UTF-8 bytes**, with at most 1,800 characters of OCR per record. These are actual text limits, not a claim of exact tokenizer counts. The separately bounded question is at most 8,000 characters. Gemini's output budget is 2,048 tokens.
7. Show the actual outgoing evidence for confirmation. When sensitive-text redaction is enabled, apply it to this preview and request, including older retained evidence. Validate Gemini's structured citations against only IDs actually included in the request; reject unsupported IDs. The system prompt requires missing-evidence explanations and separates observations from inferences.

An unmatched topic query produces a local no-evidence message and no Gemini call. A retrieval failure is shown separately. No random or unrelated records are added just to fill a prompt.

The Search model picker and Gemini Settings now use the same `model` preference. Earlier selections mistakenly written to `gemini_model` are migrated once. Each request snapshots its selected model/key; cancelled connection tests cannot clear or overwrite a newer request. The evidence-review action becomes available only after submitting evidence. Google response bodies have a bounded read size.

BM25 is lexical retrieval: paraphrases without shared terms, unsupported date expressions, non-Latin OCR, and missing/private screens can still produce incomplete results. Citation membership checks cannot prove that a claim is entailed by its source. Small contexts and grounded prompts reduce noise; they do not guarantee an error-free answer. Use citations to inspect the original moments.

Implementation: `RetrievalPolicy.kt`, `HistoryDb.retrieve`, `EvidencePolicy.context`, and `MainActivity.confirmEvidence`. No database migration or cloud vector store is needed, so existing history is immediately searchable.

References consulted: [SQLite FTS4 matchinfo and ranking](https://www.sqlite.org/fts3.html#the_matchinfo_function), [Gemini structured output](https://ai.google.dev/gemini-api/docs/structured-output), [3.5 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite), [3.1 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite). jCodeMunch supplied Screenpipe's indexed `paired_capture_loop_for_monitor` and `buildMeetingChatPrompt`; the latter constrains evidence/time ranges, flags partial transcripts and forbids invented facts. The Android BM25 implementation uses documented SQLite statistics rather than claiming to copy an upstream BM25 implementation; the index's freshness was unknown and its text search returned no verified BM25 example.
